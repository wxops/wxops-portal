## v0.5.1 — Observability Completion

v0.5.0 gave you the *context* layer — what's deployed, what's healthy, what's firing. It couldn't
tell you how a service was actually performing: metrics links showed cAdvisor CPU, not application
data, because nothing in the platform emitted a real metric. This release closes that gap — and it's
the first release that isn't portal-only: it spans `wxops-templates`, `wxops-core`,
`wxops-gitops-infrastructure`, and this repo, in a hard dependency order. **This note covers the
portal side, merged to main; the other three repos ship on their own schedules.**

---

## What's New

### Application metrics *(headline)*

Every golden-path template (Go, Node.js, Python) now emits a real, consistent metric contract
instead of a hand-rolled `/metrics` with two runtime gauges:

| Metric | Type | Labels |
|---|---|---|
| `http_requests_total` | counter | `method`, `path`, `status` |
| `http_request_duration_seconds` | histogram | `method`, `path` |
| `http_requests_in_flight` | gauge | — |

`path` is always the route *pattern*, never the raw URL — Prometheus runs platform-wide with no
cluster-wide cardinality limits, so this is the one rule that matters more than any other here.

The Monitoring checkbox (scaffold wizard + Edit Config) now actually works: it writes
`spec.parameters.monitoring` on the `XTenantApp`, and the composition emits a real `ServiceMonitor`
(or `PodMonitor`) carrying the `release: kube-prometheus-stack` label Prometheus Operator selects on.
**This replaces the old `prometheus.io/*` pod annotations**, which turned out to be a dead end: this
platform's `kube-prometheus-stack` has no `additionalScrapeConfigs`, so those annotations were never
actually read by anything — the toggle silently did nothing since it shipped. Enabling monitoring now
sets `spec.parameters.monitoring.enabled` and, optionally, `path`; port and scrape interval stay
composition-owned.

One new shared Grafana dashboard — P95/P99, error rate, request rate, in-flight saturation —
parameterized by `$namespace`/`$app`/`$env`, works for every golden-path service with zero per-team
configuration.

**Known gap, not silently papered over:** `$env` is a naming-suffix convention, not a real Prometheus
label — the `ServiceMonitor` sets no `targetLabels`. A real `environment` label is a tracked
fast-follow.

Full detail: [observability.md § Application metrics](docs/platform/observability.md#application-metrics).

### Catalog completeness score

Every entity now carries a computed quality score — description, owner, tags, links, lifecycle, and
(for API entities) whether a spec is actually resolvable. Shown as a badge on the entity detail page
and the catalog list. Computed fresh on every read, nothing stored or cached separately.

### Pipeline tab redesign

The CI/CD, Releases, and Dependencies cards were rebuilt for projects with real scale — daily CI
activity, dozens of releases, hundreds of packages — none of which the original cards handled: CI was
hard-capped at 5 runs, releases at 10, and packages silently truncated at 200 with no indicator.

Each card is now a compact summary with a "View all →" that opens a search and filter view: CI gets
status/branch filters and real pagination past the old 5-run ceiling, Releases gets an instant tag
search shared with the new dependency-compare picker, and Dependencies gets instant search
(FlexSearch) across name/ecosystem/version plus direct/dev/indirect filtering. The compare control
that diffs current-branch packages against a release tag is now grouped per manifest — a monorepo
with more than one manifest in the same ecosystem (this portal's own `cli/go.mod` alongside
`backend/go.mod`) no longer risks one manifest's diff being silently overwritten by another's.

Package manifests now report `truncated`/`total` instead of silently dropping entries past the cap
(raised 200 → 500), and are sorted before truncating — `package.json`'s dependency list was
previously kept in random order per request, since Go map iteration isn't stable, so which packages
got cut changed on every reload.

## API

```
GET /api/v1/catalog/entities/:kind/:name/ci?page=&limit=
GET /api/v1/catalog/entities/:kind/:name/releases?page=&limit=
GET /api/v1/catalog/entities/:kind/:name/packages/compare?ref=<tag>
```

`page`/`limit` are additive — omitting them reproduces the exact previous behavior.
`entityResponse` gains `completenessScore: { score, max, checks }`. Package manifests gain
`truncated`/`total`; the compare endpoint's diff is now `{ manifests: [{ ecosystem, file, added,
removed, bumped, baseTruncated, headTruncated }] }`, grouped instead of one flat list.

## Deferred, not shipped this release

**DORA-lite metrics** and **per-service alert scoping** were both originally scoped alongside the
above as "shippable in parallel." Research found both are blocked on a decision, not on engineering
time — DORA-lite needs an accepted proxy for "reached production" (nothing records that timestamp
today), and alert scoping needs a decision on which alerts get per-tenant treatment before the
`wxops-core` work can start. Recorded in [ROADMAP.md](ROADMAP.md) with the real blockers.

## Upgrade Notes

No new required portal environment variables.

**This release only does something if the other three repos are also deployed.** The Monitoring
toggle produces a correctly-shaped XR field regardless; it only emits a working `ServiceMonitor` once
`wxops-core`'s composition and `wxops-gitops-infrastructure`'s dashboard are live.

**Existing scaffolded services don't retroactively get the new metric contract or the fixed
monitoring wiring.** A service scaffolded before this release stays on its old `/metrics` and old
pod-annotation monitoring config until rescaffolded or manually updated.

## Known Limitations

| Limitation | Effect |
|---|---|
| `$env` is a naming-suffix convention, not a real label | Dashboard's environment variable works today, but isn't backed by a real Prometheus label yet |
| Alloy stamps a hardcoded `cluster` label | Log links cannot be scoped per cluster |
| Alertmanager receiver is `null` | Alerts are visible but route nowhere — no paging |
| Only traces flow through Alloy's OTLP pipeline | OTLP logs and metrics are dropped |
| Observability endpoints are global | One Grafana for every cluster |
