## v0.4.1 — Cluster DX & Inner-Loop Hardening

Turns the portal's cluster view into a genuine kubectl companion — developers can
browse pods, deployments, and services, copy commands, inspect container detail, and
download a working kubeconfig without ever needing to remember a namespace or pod
name. Alongside that, `wxops darlane sync` ships the delete-propagation fix and
several reliability improvements that make it practical as a primary inner-loop tool.

---

## What's New

### Cluster View — kubectl Companion *(headline feature)*

The cluster resource tabs are rebuilt from the ground up as a developer experience
surface, not a status dashboard. Every table row gives you the exact kubectl command
for that resource — no namespace memorization, no copy-pasting pod names.

#### Resource tabs

Three tabs are now available under each cluster's namespace selector:

| Tab | What it shows |
|-----|---------------|
| **Pods** | Status dot + colored label (Running / Pending / Failed / Succeeded), node assignment, hover-reveal detail button |
| **Deployments** | Ready/desired pill badge (green when healthy, amber/red when degraded), dot indicators (●●●○) for replica state |
| **Services** | Type badge (ClusterIP / NodePort / LoadBalancer), Cluster IP, port summary |

#### Expandable kubectl commands

Click any row to expand an inline command block for that resource — pre-filled with
the correct namespace and resource name, no editing required.

**Pods:**
```bash
kubectl exec -it -n <namespace> <pod> -- bash
kubectl logs -n <namespace> <pod> --tail=100 -f
kubectl port-forward -n <namespace> <pod> 8080:8080
kubectl describe pod <pod> -n <namespace>
```

**Deployments:**
```bash
kubectl rollout status deployment/<name> -n <namespace>
kubectl describe deployment <name> -n <namespace>
kubectl scale deployment/<name> --replicas=0 -n <namespace>
kubectl scale deployment/<name> --replicas=1 -n <namespace>
```

**Services:**
```bash
kubectl describe service <name> -n <namespace>
kubectl port-forward service/<name> -n <namespace> <port>:<port>
```

Every command has a per-line copy button that appears on hover.

#### Pod detail drawer

The "details" button on any pod row opens a slide-in right panel without leaving
the page. The drawer shows:

- **kubectl commands** — exec, logs, port-forward, describe (always shown, no extra
  fetch required)
- **Container image** — with a copy button; shows ready/restart status
- **Resource table** — cpu and memory requests vs limits side by side
- **Environment variables** — key, value, source badge:
  - `secret` (amber) — value masked as `***` on the backend; plaintext never reaches the browser
  - `cm` (cyan) — from a ConfigMap
  - `field` (purple) — downward API
  - `env` (muted) — literal value
- **envFrom bulk imports** — listed as `secret/name` or `cm/name` pills
- **Volume mounts** — name → mountPath, with a `ro` badge for read-only; SA token
  mounts (`/var/run/secrets/kubernetes.io`) are filtered out

Multi-container pods show a tab bar to switch between containers. Refresh button
in the header reloads detail without closing the drawer. `Escape` or backdrop click
closes.

#### ResourceQuota strip

A compact strip above the tabs shows namespace resource usage at a glance:

```
cpu  200m / 4    memory  512Mi / 8Gi    pods  3 / 20
```

Quota is fetched per namespace on selector change and shown regardless of which
tab is active.

#### Services tab — in-cluster DNS names

Expanding a service row shows its full in-cluster DNS name generated client-side
with a copy button:

```
<service>.<namespace>.svc.cluster.local
```

Plus a port detail table (name, protocol, port, targetPort, nodePort for NodePort
services).

#### Auto-refresh

All three tabs refresh every 30 seconds. A countdown shows the time to the next
refresh. During a background refresh the table fades to 60 % opacity so the user
can see data is being updated without a hard reload.

#### Pod health strip

Above the Pods tab, a one-line strip counts pods by status:
```
3 Running · 1 Pending · 0 Failed
```

### Bug Fix — Pinniped Kubeconfig CA Bundle

The exec-credential kubeconfig generated by `GET /api/v1/clusters/:id/kubeconfig`
was passing the **spoke cluster CA** as both `--concierge-ca-bundle-data` and
`--ca-bundle-data`. These are two different certificates:

| Flag | Purpose | Correct source |
|------|---------|----------------|
| `--concierge-ca-bundle-data` | Concierge mTLS endpoint TLS CA | Spoke cluster CA (`ca-bundle` in the cluster Secret) |
| `--ca-bundle-data` | Pinniped Supervisor OIDC endpoint TLS CA | `OIDC_CA_BUNDLE` / `OIDC_CA_BUNDLE_FILE` |

Using the wrong CA caused `pinniped login oidc` to fail TLS verification against
the Supervisor when the two CAs differ — the common case for private Supervisor
deployments.

**Fixed behavior:**

- `--ca-bundle-data` now uses `OIDC_CA_BUNDLE` (the Supervisor CA)
- When `OIDC_CA_BUNDLE` is not set (public CA, e.g. Let's Encrypt), `--ca-bundle-data`
  is **omitted entirely** so `pinniped login oidc` falls back to the system root pool
- `--concierge-ca-bundle-data` is unchanged — continues to use the spoke cluster CA

No configuration changes required. If your Supervisor uses a publicly trusted
certificate, nothing needs to be set. If you were already setting `OIDC_CA_BUNDLE`,
the kubeconfig will now work correctly.

### `wxops darlane sync` — Reliability Improvements

| Fix / Feature | Detail |
|---|---|
| **Delete propagation (bug fix)** | Files and directories deleted locally are now removed from the pod on the next flush via `kubectl exec rm -rf`. Previously only `Write`/`Create`/`Rename` events were handled; `Remove` was silently dropped. |
| **Delete-before-create ordering** | When a file is deleted then immediately recreated (e.g. a build tool replace-in-place), the delete is flushed before the new content is synced — ensuring the pod sees the correct final state. |
| Initial full sync | On startup the tool syncs all non-excluded files before incremental events begin. Suppressed with `--no-initial-sync`. |
| Max-debounce cap (2 s) | A continuous burst (e.g. `go build` emitting hundreds of files) no longer blocks syncs indefinitely — flush fires at the 2-second mark regardless of incoming events. |
| kubectl retry | Both sync and delete calls are retried up to 3 times (2 s delay) so the session survives a pod restart mid-watch. Prints `⚠  pod not ready, retrying (N/3)…` to stderr. |
| Pod-replaced re-seed | When a retry recovers (pod was replaced), the session automatically re-seeds all local files to the new pod. Prints `⟳  pod replaced — re-seeding: N file(s)`. Fires even when `--no-initial-sync` was set. |
| Cleaner output | Consistent `↑  synced` / `✗  deleted` prefixes; file names listed inline (up to 5, then `… and N more`). |
| Graceful SIGINT/SIGTERM | `Ctrl-C` flushes any pending batch then prints `stopped.` before exiting — no half-applied changes left in the pod. |

### `wxops darlane` — Inner-Loop DX *(headline feature)*

A suite of improvements that makes `darlane` a first-class inner-loop tool rather
than a raw file-sync wrapper.

#### Colored startup summary and pre-flight checks

Before the watcher starts, `darlane sync` and `darlane push` now run a full
pre-flight and print a colored startup summary:

```
 Darlane Sync

  component    python-demo
  env          dev
  namespace    tenant-rocket-team
  deployment   python-demo-darlane
  sync         /home/user/project/app/  →  /app/

  Pre-flight checks

  ✓  catalog entity found
  ✓  overlay exists
  ✓  darlane enabled
  ✓  file sync mount path  (/app/)
  ✓  language match  (python)
  ✓  tar available
```

Field labels and section headers are printed in yellow; values in bold white.
ANSI colors are suppressed automatically when `NO_COLOR` is set, `TERM=dumb`,
or stdout is not a TTY.

| Pre-flight check | Fail condition | Behavior |
|-----------------|---------------|----------|
| Catalog entity | Entity not found via API | Soft warn — watcher starts anyway (allows testing empty projects) |
| Overlay exists | No overlay in gitops-infra for this env | Soft warn |
| Darlane enabled | `darlaneEnabled: false` in overlay config | Soft warn |
| Mount path match | `--remote` differs from `fileSync.mountPath` in overlay | Soft warn + hint showing the correct path |
| Language match | Local project language ≠ catalog entity tags | Soft warn — safe to ignore for empty test repos |
| tar available | `tar --version` fails inside the pod | **Hard fail** — watcher does not start |

#### tar-unavailable hint — `kubectl debug`

When the target image has no `tar` binary (distroless, scratch, or hardened
images with a restricted security context), the CLI hard-fails with a
copy-paste ready `kubectl debug` command using the resolved pod name:

```
✗  tar not found in image — darlane sync requires tar in the container

   To attach an ephemeral BusyBox container:
   kubectl debug -it python-demo-darlane-6b4c9f7d8-xk2rv -n tenant-rocket-team \
     --image=busybox --target=python-demo-darlane

error: image does not support darlane sync
```

The pod name is resolved first via label selectors (`app=<deploy>` then
`app.kubernetes.io/name=<deploy>`) so the command is ready to run immediately.
The `--target` flag attaches the ephemeral container to the same PID namespace
as the main container — required for images that run as non-root with no shell.

#### Rollout restart tip after initial sync

When `darlaneEnabled: true` and the initial sync completes, a tip is printed
so developers know how to pick up changes that don't hot-reload:

```
→  initial sync: 42 file(s)
   tip: if the pod doesn't hot-reload, restart it:
        wxops darlane restart python-demo --local /home/user/project/app --remote /app
```

The tip includes the actual resolved `--local` and `--remote` values so it is
copy-paste ready. After the first run, `darlane restart` remembers those paths
from the session file and the flags can be omitted.

#### Pod-replaced re-seed

When `darlane sync` detects that the pod was replaced mid-session — a retry
succeeds after at least one failure — it automatically re-seeds all local files
to the new pod before resuming incremental sync:

```
⚠  pod not ready, retrying (1/3)…
⟳  pod replaced — re-seeding: 42 file(s)
↑  synced 1 file(s): app/main.py
```

This ensures the new pod always reflects full local state, not just the one file
that was pending at the moment of restart. `--no-initial-sync` is intentionally
ignored in this path — it controls startup behaviour only, not mid-session recovery.

#### `--tail-logs` flag on `darlane sync`

Stream pod logs alongside file sync events in the same terminal session without
opening a second pane:

```
$ wxops darlane sync python-demo --tail-logs

 Darlane Sync
  ...

→  initial sync: 3 file(s)
[pod] Reloading server on file change...
↑  synced 1 file(s): app/main.py
[pod] * Restarting with stat
[pod] * Debugger is active!
```

Pod log lines are prefixed `[pod]` (gray in a color TTY). The log stream
restarts automatically if the pod is replaced; `Ctrl-C` stops both the
watcher and the log stream cleanly.

### New darlane subcommands

#### `wxops darlane push`

One-shot sync — runs the pre-flight + startup summary, syncs all non-excluded
files once, then exits. Use it in CI pipelines or as a pre-run step before
launching a local dev server.

```bash
wxops darlane push python-demo --local ./app --remote /app
```

Accepts the same flags as `darlane sync` (`--local`, `--remote`, `--env`,
`--namespace`, `--deployment`, `--exclude`). Prints the rollout restart tip
when darlane is enabled.

#### `wxops darlane logs`

Tail logs from the Darlane deployment. Wraps `kubectl logs -f` with namespace
and deployment name derived from the entity's owner group.

```bash
wxops darlane logs python-demo          # follow last 100 lines
wxops darlane logs python-demo --tail 500 --follow=false
```

| Flag | Default | Description |
|---|---|---|
| `--follow`, `-f` | `true` | Stream continuously |
| `--tail` | `100` | Lines of history shown on start |
| `--env`, `-e` | `dev` | Target environment |

#### `wxops darlane restart`

Trigger a rolling restart, wait for rollout to complete (120 s timeout), then
automatically re-seed all local files into the new pod:

```
$ wxops darlane restart python-demo

↻  restarting tenant-rocket-team/python-demo-darlane…
deployment "python-demo-darlane" successfully rolled out
⟳  re-seeding: 42 file(s)…
✓  done
```

Re-seed paths are read automatically from the session file written by the last
`darlane sync` or `darlane push` invocation
(`~/.wxops/darlane-<service>-<env>.json`) — no `--local` / `--remote` flags
required. Pass them explicitly only to override.

Use `wxops darlane restart` instead of raw `kubectl rollout restart` when a
sync session is active — raw kubectl resets the pod to image state with no
re-seed.

#### `wxops darlane status`

Show per-environment Darlane status from the live promostatus API — overlay
presence, darlane flag, file-sync mount path, and current image tag with date.

```bash
wxops darlane status python-demo
```

```
Darlane status  python-demo

  dev
    overlay       ✓
    darlane       enabled
    mount path    /app/
    image tag     dev-2026-07-09_14-32-01-a1b2c3d

  staging
    overlay       ✓
    darlane       —
    image tag     v0.2.1-rc1  (2026-07-08)

  production
    overlay       —
```

### Documentation

#### Cluster RBAC on spoke clusters (`docs/deployment.md` — Step 3b)

New section with ready-to-apply manifests for the minimum RBAC required for portal
cluster tabs to work under user identity (Pinniped passes the user's groups as
RBAC subjects):

- `wxops-portal-tenant-viewer` ClusterRole — pods, services, resourcequotas, deployments (get/list)
- `wxops-portal-platform-viewer` ClusterRole — same + namespaces (for platform-team)
- `ClusterRoleBinding` for `platform-team` (cluster-wide)
- `RoleBinding` template per tenant namespace (apply when a new org is onboarded)
- Table mapping each RBAC rule to the portal feature it enables
- "When to update" guide for new clusters, new orgs, and team roster changes

#### Supervisor TLS CA scenarios (`docs/deployment.md` — Step 6)

Step 6 now covers all three certificate scenarios with a decision table:

| Supervisor certificate | Action |
|---|---|
| Let's Encrypt / public CA | Nothing — system root pool used automatically |
| Private / internal CA | `OIDC_CA_BUNDLE` or `OIDC_CA_BUNDLE_FILE` |
| Self-signed, dev only | `OIDC_TLS_SKIP_VERIFY=true` — kubeconfig will not work; use `OIDC_CA_BUNDLE` instead |

Includes an explicit warning that `OIDC_TLS_SKIP_VERIFY` does not propagate to the
generated kubeconfig because `pinniped login oidc` has no skip-verify flag.

#### `upstream-idp-name` and `FederationDomain` (`docs/cluster-registry.md`)

Clarified that `wxops.cloud/upstream-idp-name` must match
`FederationDomain.spec.identityProviders[].displayName` — **not** the
`metadata.name` of the `OIDCIdentityProvider` CR. The FederationDomain links the
two via `objectRef`. Includes a concrete FederationDomain snippet showing both
fields side by side and the `kubectl` command to find the display name on an
existing cluster. Updated `clusters.example.json` with matching inline documentation.

## New API Endpoints

| Method | Path | Description |
|--------|------|-------------|
| `GET` | `/api/v1/clusters/:id/pods/:name` | Pod detail — containers, env vars (secrets masked), volume mounts |
| `GET` | `/api/v1/clusters/:id/services` | List services in a namespace with ports |
| `GET` | `/api/v1/clusters/:id/quotas` | ResourceQuota used/hard per namespace |

All three cluster endpoints proxy to the spoke cluster under the user's Pinniped identity —
403 surfaces as an error message in the relevant tab, not a crash.

**promostatus — `fileSyncMountPath` field (extended)**

`GET /api/v1/catalog/entities/:kind/:name/promostatus` now includes
`fileSyncMountPath` per environment in the `overlays` block:

```json
{
  "overlays": {
    "dev": {
      "exists": true,
      "darlaneEnabled": true,
      "fileSyncMountPath": "/app/"
    }
  }
}
```

Used by `wxops darlane sync` to detect mount-path mismatches and by
`wxops darlane status` to display the configured path per environment.

## Upgrade Notes

No database migrations. No new required environment variables.

**OIDC_CA_BUNDLE:** If you set this for a private Supervisor CA, kubeconfigs
downloaded after this upgrade will correctly include it as `--ca-bundle-data` in
the exec credential plugin. Re-download any existing kubeconfigs to get the fix.

**Spoke cluster RBAC:** The new Pods detail drawer, Services tab, and Quota strip
require `get/list` on `pods`, `services`, and `resourcequotas`. If these are not
yet granted, those features return a 403 in the UI tab — nothing else is affected.
Apply the manifests in deployment.md Step 3b to enable them.

**wxops CLI:** Re-download the binary to get `darlane push`, `darlane logs`,
`darlane restart`, `darlane status`, and `--tail-logs`. The CLI version is stamped
at build time; `wxops version` should report `v0.4.1`.
