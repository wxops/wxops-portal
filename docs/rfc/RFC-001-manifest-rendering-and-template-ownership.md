## Summary

Kustomize base/overlay manifests, the `XTenantApp`/`XTenantDatabase` strategic-merge patches, and the
JSON 6902 patches for Darlane and per-environment database config are currently generated by Go code —
typed structs marshalled to YAML in `internal/scaffold/*.go`, plus a fair amount of raw
`fmt.Sprintf`-built YAML/JSON-patch fragments in `overlay.go`. Every change to *what* gets generated —
a new field, a different patch shape, a naming-convention tweak — requires a Go code change and a
portal backend release. This RFC opens the question of whether that coupling is worth loosening, what
"loosening" could concretely mean, and what it would cost.

## Motivation

The immediate prompt: manifest-shape changes are indistinguishable, today, from feature changes — both
require the same release cycle, the same review, the same deploy. That's arguably correct when the
change touches decision *logic* (e.g. "staging renames the XR, dev doesn't"), but it's clearly too
heavy for a change that's purely cosmetic or additive (a new optional annotation, a reordered YAML
key). There's no middle gear today.

There's a second, more structural reason to look at this now rather than later: `internal/scaffold/overlay.go`
(762 lines) is exactly the kind of file the v0.6.0 refactor is trying to get ahead of elsewhere
(`catalog.go`, `promotion-panel.tsx`, `darlane.go`, `tenant-app/main.k`) — it just wasn't named in the
original baseline. Deciding *now* whether its content should stay Go-owned, partially externalize, or
move further out changes how (or whether) it gets decomposed alongside those other four.

## Detailed Design

None of the three options below is a settled proposal — they're the shapes worth evaluating. Each is
described at the depth needed to reason about its tradeoffs, not as an implementation spec.

### Option A — Status quo: typed Go structs + inline string-templated patches

What exists today. `OverlayKustomization`, `XTenantApp`, `ExternalSecret` etc. are Go structs with
`yaml:"...,omitempty"` tags; `yaml.Marshal` produces the file bytes. The JSON 6902 patch *bodies*
(the actual `- op: add / path: ... / value: ...` blocks for Darlane, ingress host, database tier) are
already **not** struct-typed — they're built with `fmt.Sprintf` and `strings.Builder` directly into
YAML strings, then embedded as a `Patch: string` field on `PatchRef`. So "status quo" is already a
two-tier hybrid: typed containers, stringly-typed contents.

**What it gets right:** the invariants that matter most are enforced at compile time or by the type
system, not by convention — `omitempty` on `appName`/`namespace`/`image` in the overlay patch is *why*
those fields correctly inherit from base; the `images:` field simply doesn't exist as a struct field,
so there is no code path that could accidentally emit it. Naming conventions
(`argoAppName`/`xrName` in `handlers/observability.go` vs. the equivalent logic in `overlay.go`) are
Go functions that this session's new test suite (`overlay_test.go`, `observability_test.go`) now pins
directly — a rename in one without the other breaks a test, not just runtime behavior three steps later.

**What it costs:** every shape change is a Go change, a PR, a release. There is no way for a
platform engineer who isn't comfortable in the Go codebase to iterate on manifest shape.

### Option B — Externalize the literal fragments, keep decision logic and invariant checks in Go

Move the string-templated portions (already isolated as `fmt.Sprintf` blocks) into real `.tmpl` files
executed via `text/template`, loaded through `embed.FS` (still shipped inside the binary, still
versioned with a release — this doesn't yet solve "no release needed") or, as a second step, loaded
from an external, operator-supplied ConfigMap/repo (this *does* solve it, at the cost of a new
config-loading and validation surface). The Go code keeps 100% of the *decision* logic — which
template to select for dev vs. staging/production, what values to pass in — and, critically, keeps a
post-render validation pass that checks the non-negotiable invariants regardless of what the template
produced (no `images:` key, `image-transformer.yaml` present, name matches what
`handlers/observability.go` expects).

**What it gets right:** closes most of the "release needed for a text tweak" gap without touching who
owns the decision tree. The validation pass turns implicit guarantees (today: "the Go code just
doesn't have a code path for the bad case") into explicit, testable assertions — arguably a net
improvement in auditability even if nothing else changes.

**What it costs:** a template-execution and validation layer that doesn't exist today. Loses some
compile-time safety — a malformed template is now a runtime error path that needs its own test
coverage, not a compiler error. If templates become externally loaded (not `embed.FS`), that's a new
trust boundary: something has to sign, review, or otherwise gate what gets loaded, or a compromised
config source can now shape every tenant's manifests.

### Option C — Portal as thin orchestrator; kustomize "logic" is user/template-repo owned

The portal stops owning manifest *shape* at all beyond wiring: it renders variables into a template a
user/team supplies (via `wxops-templates`, similar to how `template.yaml` already drives runtime
selection today), commits the result, opens the PR. All Kustomize/XR structure, patch strategy, and
naming become the template author's responsibility.

**What it gets right:** this is the version that actually removes the coupling entirely, and it lines
up with the "integrate with what's already there" philosophy in `ecosystem-tool-strategy.md` — a team
that already has strong opinions about ingress, TLS, or patch strategy stops fighting the golden path
instead of working with it.

**What it costs, concretely, from what this session verified by reading and testing the current code:**
- **Cross-file naming coupling breaks silently.** `xrName`/`argoAppName` in `overlay.go` and the
  *identical* derivation in `handlers/observability.go` have to produce the same string for the
  Runtime tab to find the right ArgoCD Application/XR. If a user template renames things differently,
  the failure mode is not an error — it's the Runtime tab quietly rendering "unreachable" for a
  perfectly healthy service. Nothing in Option C's world catches that at review time unless the portal
  re-derives the expected name and cross-checks it, which is itself new Go code with its own edge cases.
- **The specific invariants CLAUDE.md already enforces stop being enforceable.** No static `images:`
  block (breaks Image Updater), `image-transformer.yaml` required, Image Updater CR naming pattern,
  Kustomize base+overlay structure mandatory. These are described in the project's own instructions as
  "non-negotiable," not stylistic — Option C would need an equivalent enforcement mechanism (a schema
  validator, a required lint step in the template repo's own CI) or these silently become "advisory."
- **This is arguably not a smaller problem, just a relocated one.** Instead of "Go code enforces X,"
  it becomes "a linter/schema enforces X against arbitrary user YAML," which is a harder validation
  problem, not an easier one — and now it has to run somewhere (template-repo CI? portal at PR-open
  time? both?).

### Option D — Helm rendering in the backend (ruled out; documented here for completeness)

**Already excluded by existing project decisions** — `CLAUDE.md` §What NOT to Do: "Don't add Helm
template rendering to the portal backend (read values files as plain YAML)"; `ROADMAP.md`'s
Architecture Decisions table: "Config per environment → Kustomize overlays → *Portal reads plain YAML,
no rendering engine*." This isn't re-litigated by this RFC — flagged only so a reader who hasn't seen
those docs doesn't independently propose it. The same minimalism reasoning that rules out a Backstage
runtime applies here: one fewer rendering engine, one fewer plugin/chart ecosystem, smaller review
surface for a security posture whose whole pitch is "you can read the code that proves it."

## Drawbacks

| Option | Primary drawback |
|---|---|
| A — status quo | Every manifest-shape change costs a full release cycle, regardless of how small |
| B — externalize fragments | New template-execution + validation layer to build and maintain; if externally loaded, a new trust boundary needs an owner |
| C — user/template-owned | Loses compile-time and cross-file invariant enforcement; trades a Go-code validation problem for a schema/lint validation problem that's arguably harder, not easier |
| D — Helm | Already ruled out; listed for completeness only |

## Alternatives

Approaches not covered above, noted briefly so they aren't re-proposed from scratch later:

- **CUE or KCL instead of Go templates/structs.** `wxops-core` already uses KCL for compositions
  (`kcl/tenant-app/main.k`), so there's a real argument for pulling the *portal's* generation logic
  toward the same language the platform team already maintains elsewhere, rather than adding a third
  templating approach (Go structs + Go templates + KCL). Not explored in depth here because it would
  mean embedding or shelling out to a KCL evaluator from the Go backend — a real new dependency, not a
  refactor.
- **ArgoCD `ApplicationSet` generators** doing more of the per-environment fan-out instead of the
  portal hand-rolling per-env overlay content. Tangential to this RFC — it would change *deployment*
  topology, not manifest *content* generation, but worth naming since it touches the same "who owns
  per-env variation" question from a different angle.
- **JSON Schema-validated partial overrides** — a middle ground narrower than Option C: the portal
  still owns the full manifest shape, but exposes a schema-validated "extra fields" escape hatch
  (labels, annotations, sidecar containers) that a team can set without a portal code change, while
  everything covered by the golden-path contract stays exactly as Option A today.

## Rollout Plan

Deliberately unscheduled — this section names *sequencing constraints*, not dates.

1. **Must not start before, or in parallel with uncoordinated changes to,** the v0.6.0 refactor's
   decomposition of `internal/scaffold` (not yet named as a workstream, but the same "small,
   single-purpose PRs, never mix refactor with feature" rule from
   [`refactor-and-hardening.md`](../development/refactor-and-hardening.md) applies here even more —
   this RFC is exactly the kind of design decision that should land *before* a file gets split, not
   fought over mid-split).
2. If Option B is chosen: land the `overlay_test.go`/`observability_test.go` coverage this session
   added as the safety net *first* (already done), then extract one already-isolated fragment (the
   Darlane patch body is the obvious first candidate — it's already a self-contained
   `BuildDarlanePatch` function) into a template as a spike, keep it behind nothing user-visible, and
   confirm the golden-output tests still pass byte-for-byte before extracting anything else.
3. If Option C is on the table at all: it should be evaluated *together with*
   `fleet-sync-and-golden-path-evolution.md`'s Part A (file classification: Platform-owned /
   Governance-owned / Scaffold-owned) — that classification is directly reusable for deciding which
   parts of a manifest a team could plausibly own under Option C and which must stay platform-owned
   regardless of which option wins.
4. No production behavior should change as a side effect of picking an option — this mirrors the
   refactor release's own rule: extraction and relocation first, behavior changes (if any) are a
   separate, later, explicitly-scoped PR.

## Open Questions

Grouped by theme. None of these have to be answered before more get added — that's the point of
opening this now rather than after a design is half-built.

**Ownership boundary**
1. What's the actual unit of "a release-worthy change" vs. "a tweak"? Is there a crisp line, or does
   it turn out every case needs judgment (in which case Option B's validation layer is doing the real
   work, not the template mechanism itself)?
2. If Option C ever becomes real: which pieces of the manifest can a team own outright, and which are
   permanently platform-owned regardless of template choice (ingress shape? database tier semantics?
   Darlane's field contract, given `XDarlane` is a planned standalone XRD)?

**Invariant enforcement**
3. If manifest shape moves out of Go structs, what replaces "the compiler won't let you emit
   `images:`"? A JSON Schema? A required `kustomize build --dry-run` + grep step in CI? Who owns that
   check when it lives outside the portal's own test suite?
4. How do we keep `xrName`/`argoAppName`-style cross-file naming coupling from becoming a second,
   independent source of truth the moment generation logic isn't all in one Go package?

**Versioning & compatibility**
5. Does this need its own lock-file concept, or does it fold into
   `fleet-sync-and-golden-path-evolution.md`'s `.wxops/template.lock.yaml` idea (Part A)? They're
   solving adjacent but distinct problems — that doc is about *application* template drift, this one
   is about *manifest-generation* logic — do they end up as one mechanism or genuinely two?
6. What happens to already-scaffolded services if the generation mechanism changes under them? Is
   there a migration, or does "generated once, frozen forever until re-promoted" (already roughly true
   today) stay true under every option?

**Trust & security boundary**
7. Under Option B with externally-loaded templates: who can change what's loaded, and is that gated
   the same way Vault/Gitea writes already are (portal create/update-only, PR-reviewed, no direct
   writes)?
8. Under Option C: does accepting a team-authored Kustomize/patch template change the portal's
   "read-only to clusters" trust story at all, given the portal still never applies anything directly —
   or is the risk purely "wrong output gets promoted," which is a correctness problem, not a security
   one?

**Testing & quality gate**
9. Does this ride on the same golden-snapshot pattern `refactor-and-hardening.md`'s K1 workstream
   wants for `wxops-core`'s KCL compositions — i.e., commit expected rendered output and diff against
   it in CI — applied to whichever mechanism wins here?
10. If templates move outside the Go binary, how does test coverage travel with them? A `.tmpl` file
    living in a different repo needs its own test story, not just portal-side unit tests.

**Scope check**
11. Is the actual, specific pain point a *hypothetical* ("this could get annoying eventually") or is
    there a concrete recent example — a real kustomize/overlay tweak that forced a backend rebuild and
    shouldn't have? Naming one would sharpen every option above considerably.
12. Does this need to be decided as one RFC, or does it split cleanly into "should fragments become
    templates" (a scoped, mechanical question) and "should teams own manifest shape" (a product/trust
    question with much higher stakes) — i.e., should this RFC fork into RFC-001 and RFC-002 once the
    brainstorm settles?
