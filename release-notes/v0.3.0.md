## v0.3.0 — Platform Visibility

The largest release since v0.2.0. Makes the platform fully observable — every service's
deployment state, image tags, and lifecycle are visible at a glance — and introduces a
complete UI-driven promotion workflow that replaces the removed ArgoCD webhook.

---

## What's New

### Catalog Search & Filtering

The catalog is now fully searchable and filterable without a page reload.

- **Full-text search** — `?search=` matches name, title, description, and tags across all
  entities. Powered by in-process filtering on the backend's cached entity slice.
- **Owner filter** — `?owner=rocket-team` returns entities owned by a team. The `group:`
  prefix is stripped automatically.
- **Kind filter pills** — All / System / Component / API / Resource / Group / Doc tabs
  above the entity list.
- **Lifecycle tabs client-side** — the full entity dataset is fetched once (backend 5-min
  cache), then lifecycle tabs filter in-browser. Tab counts are always accurate with no
  pagination mismatch.
- **Cache invalidation webhook** — `POST /api/v1/webhooks/catalog/refresh` (Bearer token)
  flushes the in-memory cache immediately. Wire to the `gitops-infra` Gitea push webhook
  to make new catalog commits visible instantly instead of waiting up to 5 minutes.

### Global Command Palette (Ctrl+K / Cmd+K)

Find any entity without leaving the keyboard.

- FlexSearch `Document` index built in-browser on first open (prefix tokenization for instant
  partial matches), 5-min TTL matching the backend cache
- Searches name, title, description, and tags across all entity kinds simultaneously
- Keyboard navigation: ↑↓ to move, Enter to navigate, Esc to dismiss
- Kind color badges and lifecycle hints on each result row; concurrent-open deduplication
- Sidebar "Search…" button triggers the same palette

### Session Notifications

The bell icon in the top bar surfaces portal activity during your session.

- Fires on: project scaffolded, project imported, entity registered (PR opened)
- Background poll every 3 minutes detects catalog merges by comparing entity count to your
  session baseline → shows "Catalog updated: N new entries"
- Backed by `sessionStorage` — cleared automatically when the tab or session ends

### Dracula-Inspired Dark Mode

Dark theme overhauled to reduce eye strain during extended use.

- Background: `#282a36`-tone (L=0.20 — not near-black, has visible depth)
- Accent: lavender purple `#bd93f9`-tone for all interactive elements
- Muted text: Dracula comment color `#6272a4` (blue-purple instead of flat gray)
- Foreground: warm off-white `#f8f8f2`

### Environment Version Row

Each Component detail page now shows the latest image tag deployed per environment.

- Three-column card: **Dev** (blue) / **Staging** (amber) / **Production** (green)
- Dev tags shown as `dev-…-{sha7}` (abbreviated); staging/production shown in full
- Relative timestamps: "today / yesterday / 5d ago / 2mo ago"
- Card hides when no tags exist — no empty-state noise
- New endpoint: `GET /api/v1/catalog/entities/:kind/:name/versions`

### Container Image Environment Badges

The Releases card now makes it obvious which image belongs to which environment.

- Each image row has a colored left border + tinted background matching its environment
- Inline environment badge (dev / staging / prod) with color dot
- SHA-256 digest tags filtered out — they are noise, not deployable versions
- Header count reflects the filtered set, not the raw registry count

### Lifecycle Promotion UI *(headline feature)*

Full lifecycle promotion is now UI-driven, replacing the removed ArgoCD webhook.

#### New lifecycle model

```
experimental ──► development ──► staging ──► production
     │                                            │
     └────────────── deprecated ─────────────────┘
```

- **`experimental`** = catalog entity only; no overlay, no deployment
- **`development`** = dev overlay on `gitops-infra` main; dev image tag present
- **`staging`** = staging overlay merged; `v*-rc*` image tag present
- **`production`** = production overlay merged; `v*` release tag present
- **`deprecated`** = locked; removal PR open for platform-team review

#### Scaffold breaking change

The scaffold **no longer generates `overlays/dev/`**. The infra PR now contains base
manifests only. Developers create the dev overlay through the Promotion panel when ready.

#### Promotion panel — two-step flow

The **Promotion** card appears on every scaffolded Component detail page.

**Step A — Create overlay PR:**
1. Developer clicks "Create overlay" on the target environment row
2. Inline config form expands: replicas, ingress host, CPU/memory limits (all optional)
3. Portal opens a PR in `gitops-infra` titled `[Promote] {team}/{app} → {env}`
4. Platform-team reviews and merges

**Step B — Confirm lifecycle:**
1. Panel detects overlay on `main` and shows "Confirm"
2. One click updates the catalog lifecycle

If a promotion PR is already open, the row shows "PR #N pending" — preventing duplicates.

#### Overlay configuration options

The overlay wizard exposes per-environment configuration for the database, ingress, resources, and Vault secrets.

**Database tiers**

| Tier | Behaviour |
|---|---|
| **Shared** | Assigns to an existing CNPG cluster pool. `env` selectable for dev/staging overlays (e.g. staging can share the dev pool). Production always targets `prod`. |
| **Dedicated** | Provisions a new CNPG cluster for this app only. Namespace is always `cnpg-system`. Environment badge is read-only — fixed to the overlay's own environment. |

Dedicated options: instances, storage size, PostgreSQL version.

**PgBouncer pooler (dedicated only)**
The connection pooler checkbox defaults to **enabled** — this matches the `XTenantDatabase` CRD's own default. Uncheck to explicitly write `enablePooler: false` and disable it; the field is always emitted in the generated overlay so the CRD default is never silently applied.

**Database naming**
Default: `{appName}-{env}-db` (e.g. `python-demo-dev-db`, `python-demo-staging-db`, `python-demo-production-db`). The per-environment suffix prevents accidental cross-environment sharing. Override is allowed.

**XTenantDatabase environment mapping**
The CRD accepts `dev`, `staging`, `prod` only. The portal automatically maps `production` → `prod`. For shared tier on dev/staging overlays, the environment can be overridden via a select; for production and all dedicated overlays the value is fixed and shown as a read-only badge.

**Vault secrets on edit**
On `create-overlay`, at least one Vault secret is required. On `update-overlay` (edit mode), secrets already exist at the path — the list can be left empty to preserve them unchanged, or populated to update specific keys.

#### Deprecation

Managers and platform-team can deprecate from the Promotion panel.

- Writes `wxops.cloud/deprecated`, `wxops.cloud/deprecated-reason`, `-by`, `-at` annotations
- Updates lifecycle to `deprecated`
- Opens `[Deprecate]` PR in `gitops-infra` with a `DEPRECATED.md` marker
- Entity locked — promotion panel shows a deprecation banner; all actions disabled

#### Permission matrix

| Transition | Who can trigger |
|---|---|
| experimental → development | Any team member, Managers, platform-team |
| development → staging | Managers or platform-team only |
| staging → production | Managers or platform-team only |
| Deprecation | Managers or platform-team only |

#### New endpoints

| Method | Path | Description |
|--------|------|-------------|
| `GET` | `/api/v1/catalog/entities/:kind/:name/promostatus` | Overlay existence, open PRs, tags per env |
| `POST` | `/api/v1/catalog/entities/:kind/:name/promote` | `action: create-overlay` or `confirm` |
| `POST` | `/api/v1/catalog/entities/:kind/:name/deprecate` | Deprecate with reason, open removal PR |

#### Removed

| Method | Path | Reason |
|--------|------|--------|
| `POST` | `/api/v1/webhooks/promote/:kind/:name` | Replaced by UI-driven promotion |

#### Lifecycle removed from edit panel

The lifecycle field has been removed from the entity edit form. Use the Promotion panel.

### Team Ownership View

The Group detail page now shows the full picture of what a team owns and depends on.

- **APIs** section — API entities owned by this team
- **Resources** section — Resource entities (databases, queues, etc.) owned by this team
- **Consumes** section — external APIs this team's components declare in `consumesApis`

### Import Wizard Pagination

Large teams with many repositories can now load them incrementally.

- Repo listing shows "Showing N of total" count
- "Load more (N remaining)" button appears when there are more repos; fetches 50 at a time

### Register Entity Form — Step Indicator and Live YAML Preview

The entity registration form now matches the scaffold wizard's layout and UX.

- **Step indicator** at the top of the form — numbered pill badges with connector lines (`1 Details → 2 Review`), same visual style as the scaffold wizard
- **Live YAML preview** on the right (`lg:grid-cols-2` layout) — updates on every keystroke as you fill in the form, showing the exact YAML that will be committed; dashed placeholder before the form has content
- **Review step** before submitting — step 2 shows a summary card on the left (kind, name, owner, system, draft status) and "Confirm YAML" on the right; no surprises on submission
- **Draft / Published** badge on the YAML panel for Doc entities

### Doc Entity Improvements

Doc entity creation and editing now has first-class support.

- **Direct commit to `main`** — Doc entities (RFC, ADR, documentation) are committed directly to `gitops-infra/catalog/` when created or updated; no PR gate. Cache is invalidated immediately so the document appears in the catalog without the usual 5-minute TTL wait.
- **Author-only draft visibility** — `spec.draft: true` hides a Doc from everyone except the author (matched by session username) and `platform-team`. Previously draft visibility was team-scoped; now it is author-scoped. When published (`draft: false`), the document becomes visible to all authenticated users.
- **System field in register form** — the Doc creation form now includes a System dropdown (previously missing).
- **`docStatus` editing** — segmented control with color-coded status values: `proposed` / `under-review` / `accepted` / `deprecated` / `superseded`.
- **`relatedTo` editing** — Doc entities can now link to Components, APIs, and Resources directly from the edit panel. System is excluded (linking a Doc to a System is redundant with `spec.system`).
- **Owner and System pre-population** — the edit panel now correctly pre-selects the entity's current owner and system values. Previously the dropdowns opened blank even when values existed in the YAML.

### Catalog Entity Edit Panel

- Owner and System dropdowns now pre-populate with the entity's current values on open
- Sub-team groups (`rocket-team:Owners`, `rocket-team:Managers`) are excluded from all Owner dropdowns — only top-level team groups are shown
- `relatedTo` editing available for Doc entities (Component, API, Resource targets only)

### Deprecation Confirmation Dialog

Clicking "Deprecate this service" now opens a confirmation dialog instead of an inline form.

- Fixed overlay with backdrop blur; auto-focuses the reason textarea on open
- Escape key and backdrop click dismiss the dialog
- "Deprecate" button is disabled until a reason is entered — prevents accidental empty deprecations
- Deprecate trigger is a caution-styled outlined button with a warning icon (replaces the previous plain text link)

## Breaking Changes

1. **Scaffold no longer generates `overlays/dev/`** — projects scaffolded after this release
   start at `experimental`. Use the Promotion panel to create the dev overlay.
   > *Existing projects:* already have `overlays/dev/` committed. Use the Promotion panel's
   > **Confirm** button to reconcile the lifecycle.

2. **`POST /api/v1/webhooks/promote/:kind/:name` removed** — remove any ArgoCD notification
   or CI script calling this endpoint. Promotion is now portal UI-driven.

3. **Lifecycle removed from edit panel** — direct lifecycle edits via the entity edit form
   are no longer possible. Use the Promotion panel.

## Upgrade Notes

No database migrations. No new required environment variables.

**Optional — cache invalidation webhook** (recommended):

In Gitea → `gitops-infra` repo → Settings → Webhooks → Add:
- URL: `https://<portal-host>/api/v1/webhooks/catalog/refresh`
- Method: POST
- Authorization: `Bearer <WEBHOOK_TOKEN>` (same token as scaffold webhooks)
- Trigger: Push events

Without this, catalog updates are visible within 5 minutes (existing TTL).
