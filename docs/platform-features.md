# Platform Features — XTenantApp, Database, and Vault

This document covers the full XTenantApp and XTenantDatabase spec schemas, the ExternalSecret
path conventions, and how the portal backend constructs each manifest from a `CreateProjectRequest`.

---

## Architecture Overview

```
CreateProjectRequest (POST /api/v1/scaffold/projects)
    │
    ├─→ NewXTenantApp()        → base/xtenant-app.yaml
    ├─→ NewXTenantDatabase()   → base/xtenant-database.yaml   (if database enabled)
    ├─→ NewEnvExternalSecret() → base/external-secret-env.yaml (if vaultSecrets enabled)
    ├─→ NewDbExternalSecret()  → base/external-secret-db.yaml  (if databaseSecrets enabled)
    └─→ kustomize.go           → base/kustomization.yaml
                                 overlays/{dev,staging,production}/kustomization.yaml
                                 overlays/{env}/patch-xtenant-app.yaml
                                 overlays/{env}/image-transformer.yaml
```

Per-environment fields (replicas, resources, ingress host, DB tier/cluster) are never
written to the base — they are JSON 6902 patches in each overlay's `kustomization.yaml`,
generated by the Promotion panel flow, not the scaffold wizard.

## XTenantApp

**APIVersion:** `platform.wxops.cloud/v1alpha1`
**Kind:** `XTenantApp`
**Source:** `backend/internal/scaffold/xtenant_app.go`

### Full Spec Schema

```go
type XTenantAppParams struct {
    // Identity — set in base, never patched
    AppName   string `yaml:"appName,omitempty"`
    Namespace string `yaml:"namespace,omitempty"`

    // Image — base sets registry/{team}/{appName}:latest;
    // ArgoCD Image Updater overwrites after every CI build
    Image            string   `yaml:"image,omitempty"`
    ImagePullSecrets []string `yaml:"imagePullSecrets,omitempty"` // default: ["regcred"]

    // Template metadata — catalog / scaffold bookkeeping
    AppFlavor  string          `yaml:"appFlavor,omitempty"`
    TemplateID string          `yaml:"templateId,omitempty"`
    Repository *RepositorySpec `yaml:"repository,omitempty"` // URL: {giteaURL}/{team}/{appName}

    // Container — env-agnostic
    ContainerPort *int32        `yaml:"containerPort,omitempty"`
    Resources     *ResourceSpec `yaml:"resources,omitempty"` // ← OVERLAY ONLY, not in base

    // Replica count — env-specific, always in overlay
    Replicas *int32 `yaml:"replicas,omitempty"` // ← OVERLAY ONLY

    // Static env vars and sources
    Env     []EnvVar        `yaml:"env,omitempty"`
    EnvFrom []EnvFromSource `yaml:"envFrom,omitempty"`

    // Annotations forwarded to the Pod spec
    PodAnnotations map[string]string `yaml:"podAnnotations,omitempty"`

    // Secrets: which K8s secrets the composition should mount into the pod
    SecretsFrom *SecretsFromSpec `yaml:"secretsFrom,omitempty"`

    // Platform feature toggles — declared in base, inherited by all overlays
    RolloutStrategy *RolloutStrategy `yaml:"rolloutStrategy,omitempty"`
    Reloader        *ReloaderSpec    `yaml:"reloader,omitempty"`
    Probes          *ProbesSpec      `yaml:"probes,omitempty"`
    Service         *ServiceSpec     `yaml:"service,omitempty"`
    Ingress         *IngressSpec     `yaml:"ingress,omitempty"`

    // Debug pod — overlay-only, injected by Promotion panel / wxops debug
    Darlane *DarlaneSpec `yaml:"darlane,omitempty"` // ← OVERLAY ONLY
}
```

### Base vs Overlay Split (enforced by NewXTenantApp)

`NewXTenantApp()` in `xtenant_app.go` only populates fields that are
environment-agnostic. It deliberately leaves `Replicas`, `Resources`, and
ingress `Host`/`ClusterIssuer` nil — these are patched by each overlay.

```go
// Base sets: AppName, Namespace, Image, ImagePullSecrets, AppFlavor, TemplateID,
//            ContainerPort, Repository, SecretsFrom, Ingress (enabled + TLS/auth flags),
//            Reloader, Probes, RolloutStrategy, PodAnnotations (monitoring), Env
//
// Base does NOT set: Replicas, Resources, Ingress.Host, Ingress.TLS.ClusterIssuer, Darlane
```

`MergeEnvPatch(base, patch)` reconstructs the effective config by overlaying a
dev patch onto the base — used by `GetProjectConfig` to return a unified view
to the edit-config UI.

### SecretsFrom

```go
type SecretsFromSpec struct {
    App      *SecretRefToggle `yaml:"app,omitempty"`
    Database *SecretRefToggle `yaml:"database,omitempty"`
}

type SecretRefToggle struct {
    Enabled    bool   `yaml:"enabled"`
    SecretName string `yaml:"secretName,omitempty"` // overrides default if set
}
```

Generated when `req.VaultSecrets` or `req.DatabaseSecrets` is true. The composition
reads this field to decide which K8s Secrets to mount into the pod via `envFrom`.

Default secret names (if `SecretName` not overridden):
- App: `{appName}-env`
- Database: `{appName}-db-creds`

The `SecretName` override on Database is set only when `DbSecretTarget(appName, "")` returns
something other than `{appName}-db-creds` — e.g. when the user provides a custom `dbName`.

### Ingress

```go
type IngressSpec struct {
    Enabled   bool      `yaml:"enabled"`
    ClassName string    `yaml:"className,omitempty"` // filled by composition default
    Host      string    `yaml:"host,omitempty"`      // ← OVERLAY: set by Promotion panel
    Path      string    `yaml:"path,omitempty"`
    PathType  string    `yaml:"pathType,omitempty"`
    TLS       *TLSSpec  `yaml:"tls,omitempty"`
    Auth      *AuthSpec `yaml:"auth,omitempty"`
}

type TLSSpec struct {
    Enabled       bool   `yaml:"enabled"`
    SecretName    string `yaml:"secretName,omitempty"`
    ClusterIssuer string `yaml:"clusterIssuer,omitempty"` // ← OVERLAY: per-env issuer
}
```

`Enabled`, `TLS.Enabled`, and `Auth.Enabled` are base fields — they declare the
platform contract. `Host` and `ClusterIssuer` are overlay fields — they are the
environment-specific values.

### Rollout Strategy

```go
type RolloutStrategy struct {
    Type          string         `yaml:"type,omitempty"` // RollingUpdate | Recreate | Canary
    RollingUpdate *RollingUpdate `yaml:"rollingUpdate,omitempty"`
}

type RollingUpdate struct {
    MaxSurge       string `yaml:"maxSurge,omitempty"`
    MaxUnavailable string `yaml:"maxUnavailable,omitempty"`
}
```

Only set when `req.RolloutType != ""` and `req.RolloutType != "RollingUpdate"`
(since `RollingUpdate` is the composition default and omitting the field is equivalent).

### Health Probes

```go
type ProbesSpec struct {
    Liveness  *ProbeDetail `yaml:"liveness,omitempty"`
    Readiness *ProbeDetail `yaml:"readiness,omitempty"`
    Startup   *ProbeDetail `yaml:"startup,omitempty"`
}

type ProbeDetail struct {
    Enabled          bool   `yaml:"enabled"`
    Path             string `yaml:"path,omitempty"`
    PeriodSeconds    *int32 `yaml:"periodSeconds,omitempty"`
    FailureThreshold *int32 `yaml:"failureThreshold,omitempty"`
}
```

Probes are generated when `req.LivenessPath != ""` or `req.ReadinessPath != ""`.
The composition creates `httpGet` probes using the configured `Path` against `containerPort`.

### Monitoring

When `req.MonitorEnabled` is true, `NewXTenantApp` adds pod annotations:

```go
PodAnnotations["prometheus.io/scrape"] = "true"
PodAnnotations["prometheus.io/port"]   = fmt.Sprintf("%d", *req.ContainerPort)
PodAnnotations["prometheus.io/path"]   = req.MetricsPath // default: "/metrics"
```

The composition passes these through to the Pod template unchanged.

### Darlane

Darlane config is **not set at scaffold time**. It is injected as a JSON 6902 `op: add`
patch by the Promotion panel UI or `wxops debug darlane`. See `docs/darlane.md` for
the full `DarlaneSpec` schema, patch format, and TTL behaviour.

```go
type DarlaneSpec struct {
    Enabled            bool               `yaml:"enabled"`
    Replicas           *int32             `yaml:"replicas,omitempty"`
    Image              string             `yaml:"image,omitempty"`
    Command            []string           `yaml:"command,omitempty"`
    FileSync           *FileSyncSpec      `yaml:"fileSync,omitempty"`
    TrafficWeight      *int32             `yaml:"trafficWeight,omitempty"`
    StickySession      *StickySessionSpec `yaml:"stickySession,omitempty"`
    HeaderRouting      *HeaderRoutingSpec `yaml:"headerRouting,omitempty"`
    Env                []EnvVar           `yaml:"env,omitempty"`
    TTL                string             `yaml:"ttl,omitempty"`
    Resources          *ResourceSpec      `yaml:"resources,omitempty"`
    ContainerPort      *int32             `yaml:"containerPort,omitempty"`
    TelemetryPort      *int32             `yaml:"telemetryPort,omitempty"`
    ProductionOverride bool               `yaml:"productionOverride,omitempty"`
}
```

`ProductionOverride: true` is required to allow a Darlane patch on the production overlay.
The composition rejects a production Darlane configuration unless this flag is set.

## XTenantDatabase

**APIVersion:** `platform.wxops.cloud/v1alpha1`
**Kind:** `XTenantDatabase`
**Source:** `backend/internal/scaffold/xtenant_database.go`

### Spec Schema

```go
type XTenantDatabaseParams struct {
    // Project-level — set in base by NewXTenantDatabase()
    Owner                string   `yaml:"owner"`                  // team name
    Extensions           []string `yaml:"extensions,omitempty"`   // default: [uuid-ossp, pgcrypto]
    VaultSecretStoreName string   `yaml:"vaultSecretStoreName,omitempty"` // always: vault-tenant

    // Per-environment — patched by Promotion panel
    Tier             string `yaml:"tier,omitempty"`             // micro|small|medium|large
    Environment      string `yaml:"environment,omitempty"`      // dev|staging|production
    ClusterRef       string `yaml:"clusterRef,omitempty"`       // name of shared CNPG cluster
    ClusterNamespace string `yaml:"clusterNamespace,omitempty"` // namespace of CNPG cluster
    DbName           string `yaml:"dbName,omitempty"`           // Postgres database name

    // Dedicated cluster (production or compliance-isolated workloads)
    DedicatedCluster *DedicatedClusterSpec `yaml:"dedicatedCluster,omitempty"`

    // Reclaim policy — default Retain; set Delete only for ephemeral envs
    DatabaseReclaimPolicy string `yaml:"databaseReclaimPolicy,omitempty"`
}

type DedicatedClusterSpec struct {
    Instances       int32  `yaml:"instances"`
    StorageSize     string `yaml:"storageSize"`
    PostgresVersion int32  `yaml:"postgresVersion"`
    EnablePooler    bool   `yaml:"enablePooler"`
    Namespace       string `yaml:"namespace,omitempty"`
}
```

### Naming Convention

```go
// metadata.name: {team}-{appName}-db
// e.g. rocket-team-payment-api-db
dbName := req.AppName + "-db"
metadata.name = fmt.Sprintf("%s-%s", req.Team, dbName)
```

The `Tier`, `ClusterRef`, and `DbName` fields are intentionally absent from the base.
The comment in `NewXTenantDatabase` is explicit:

> "Per-environment fields (dbName, tier, environment, clusterRef) are patched via
> JSON 6902 in each overlay's kustomization.yaml through the Promote flow."

### Extensions

Default extensions when `req.DbExtensions` is empty:

```go
extensions = []string{"uuid-ossp", "pgcrypto"}
```

Custom extensions are passed in the scaffold request:

```json
{ "dbExtensions": ["uuid-ossp", "pgcrypto", "pg_trgm", "postgis"] }
```

The composition installs these on the Postgres cluster during provisioning.
Adding extensions after provisioning requires a manual Postgres `CREATE EXTENSION` or
a composition version bump.

## ExternalSecret

**APIVersion:** `external-secrets.io/v1`
**Source:** `backend/internal/scaffold/external_secret.go`

### App Secrets (NewEnvExternalSecret)

Generated when `req.VaultSecrets == true`.

```yaml
apiVersion: external-secrets.io/v1
kind: ExternalSecret
metadata:
  name: {appName}-env
  namespace: tenant-{team}
spec:
  refreshInterval: 1m
  secretStoreRef:
    name: vault-tenant
    kind: ClusterSecretStore
  target:
    name: {appName}-env
  dataFrom:
    - extract:
        key: {team}/{appName}/env
```

The composition mounts the resulting K8s Secret as `envFrom.secretRef` into the pod.

**Vault write path:** `{team}/{appName}/env`
Populate via `vault kv put {team}/{appName}/env KEY=value KEY2=value2` or the
portal's config-edit form (which calls `POST /api/v1/scaffold/projects/{team}/{app}/secrets`).

### Database Credentials (NewDbExternalSecret)

Generated when `req.DatabaseSecrets == true`.

```yaml
apiVersion: external-secrets.io/v1
kind: ExternalSecret
metadata:
  name: {appName}-db-creds
  namespace: tenant-{team}
spec:
  refreshInterval: 1m
  secretStoreRef:
    name: vault-tenant
    kind: ClusterSecretStore
  target:
    name: {appName}-db-creds
  dataFrom:
    - extract:
        key: {team}/databases/{appName}-db/connection-creds
```

The `XTenantDatabase` composition writes the Postgres connection string into this
Vault path after the cluster is provisioned. No manual writes needed for the
database credential — only for app-level secrets.

### Secret Name Helpers

```go
// ResolveDbName returns the effective Postgres database name.
// default: "{appName}-db"
func ResolveDbName(appName, dbName string) string

// DbSecretTarget returns the K8s Secret name for DB credentials.
// Avoids double -db suffix when dbName already ends with "-db".
func DbSecretTarget(appName, dbName string) string
// "" → "{appName}-db-creds"
// "payment-db" → "payment-db-creds"
// "payment" → "payment-db-creds"
```

Always use `DbSecretTarget()` when referencing the database secret — never construct
`{appName}-{dbName}-creds` manually.

### Vault Security Model

| Operation | Allowed | Notes |
|---|---|---|
| Write (create / update) | ✓ | Scaffold and edit-config write app secrets |
| Read | ✗ | Portal never reads back secret values |
| Delete | ✗ | Secrets persist even when the app is decommissioned |

The portal must verify the Gitea repo and gitops-infra config exist **before**
writing to Vault. Writing to Vault first would create orphaned secrets with no
app to consume them.

## CreateProjectRequest → XR Field Mapping

| Request field | XR | Field path |
|---|---|---|
| `appName` | XTenantApp | `spec.parameters.appName` |
| `team` | XTenantApp | `metadata.labels[wxops.cloud/team]` |
| `containerPort` | XTenantApp | `spec.parameters.containerPort` |
| `appFlavor` | XTenantApp | `spec.parameters.appFlavor` |
| `templateId` | XTenantApp | `spec.parameters.templateId` |
| `vaultSecrets` | XTenantApp | `spec.parameters.secretsFrom.app.enabled` |
| `databaseSecrets` | XTenantApp | `spec.parameters.secretsFrom.database.enabled` |
| `ingressEnabled` | XTenantApp | `spec.parameters.ingress.enabled` |
| `certManager` | XTenantApp | `spec.parameters.ingress.tls.enabled` |
| `ssoAuth` | XTenantApp | `spec.parameters.ingress.auth.enabled` |
| `reloader` | XTenantApp | `spec.parameters.reloader.enabled` |
| `livenessPath` | XTenantApp | `spec.parameters.probes.liveness.path` |
| `readinessPath` | XTenantApp | `spec.parameters.probes.readiness.path` |
| `rolloutType` | XTenantApp | `spec.parameters.rolloutStrategy.type` |
| `monitoringEnabled` | XTenantApp | `spec.parameters.podAnnotations[prometheus.io/*]` |
| `metricsPath` | XTenantApp | `spec.parameters.podAnnotations[prometheus.io/path]` |
| `envVars` | XTenantApp | `spec.parameters.env[]` |
| `podAnnotations` | XTenantApp | `spec.parameters.podAnnotations` |
| `dbExtensions` | XTenantDatabase | `spec.parameters.extensions` |

Fields not in this table (`replicas`, `resources`, `ingress.host`, `ingress.tls.clusterIssuer`,
`db.tier`, `db.clusterRef`, `db.dbName`) are overlay-only and are never accepted in the
scaffold request.

## Namespace Resolution

```go
// DefaultNamespace derives the spoke cluster namespace from the team name.
func defaultNamespace(team string) string {
    if team == "platform-team" {
        return "platform"
    }
    return "tenant-" + team
}
```

The namespace is set in the base `XTenantApp` and propagated to all `ExternalSecret`
and catalog entity manifests. It matches the `groupToTenant()` logic in
`backend/internal/handlers/clusters.go`.

## Adding New Platform Features

When the Crossplane composition gains a new `spec.parameters.*` field:

1. **Add the Go struct field** to `XTenantAppParams` (or `XTenantDatabaseParams`) in
   `backend/internal/scaffold/xtenant_app.go`.
2. **Add the request field** to `CreateProjectRequest` and `UpdateConfigRequest` in
   `backend/internal/scaffold/request.go` if it is project-level (base).
3. **Wire it in `NewXTenantApp`** — only if environment-agnostic. Overlay-only fields
   must not be set here.
4. **Update `MergeEnvPatch`** if the field can be overridden by an overlay patch and
   the edit-config UI needs to show the merged value.
5. **Update the Promotion panel** in the frontend if the field is per-environment.
6. **Update this doc** and the docs-site scaffolding/features.md.
